# Performance baseline and ranked fixes (R25, 2026-10)

A measured baseline of the production build on desktop and a throttled mid phone, the causes
behind the worst numbers (traces, long-animation-frame attribution, CPU profiles, memory-infra
dumps), and the fixes ranked by user-visible gain per effort. Nothing in the app changed; the
harness is `tools/perf/baseline.ts`. The phone's first load is covered in more depth by
`perf/phone-first-load-2026-10.md` (R23); its proposals are reused here, not repeated.

## Method

- **Build**: `origin/develop` at `c66d863`, `RECTO_RENDER_OVERRIDE=1 pnpm build`, served by the
  script's own static server with gzip (as GitHub Pages) and `max-age=600`. Attribution runs used
  the same build with `vite build --sourcemap` into a scratch directory.
- **Browser**: Playwright Chromium 1194, headless, GPU = **SwiftShader** (no hardware GPU on the
  machine). Canvas and compositing run on the CPU, so frame times are an upper bound and a trend
  between builds, not the owner's Mac (GLS-6 says the same of the glass lab).
- **Desktop**: 1440×900 at DPR 2, no throttle. **Phone**: 390×844, DPR 3, touch (the compact
  edition picks itself), CPU 4× (CDP), Lighthouse's slow 4G (1.6 Mbps, 150 ms per request) as one
  shared link in the server, because CDP's network emulation does not reach the service worker's
  own fetches.
- **Large PDF**: generated by the script (no dependency): 300 pages, 25 MiB, cycling a text page,
  an image page (two of twelve 1000×700 Flate images), a text page and a vector chart (1,500
  filled rects and a polyline).
- **Runs**: three per profile, fresh browser context each; the table gives medians. The machine
  was shared with other worktrees (load average 6–21 on 4 cores), so main-thread numbers moved
  run to run; the heavy-lock (`tools/dev/heavy.sh`) only serialises lock users. Scroll
  long-task totals are the noisiest (one run measured 46 s TBT); trust the medians and the
  ratios, not single runs.

Rerun: `cd apps/web && RECTO_RENDER_OVERRIDE=1 ../../tools/dev/heavy.sh pnpm build`, then
`tools/dev/heavy.sh node --experimental-strip-types tools/perf/baseline.ts --runs 3`
(about 45 min; `--only first,large,scroll,memory,ink,work`, `--profiles`, `--trace`,
`--cpu-profile`, `--memory-dump`, `--dist <sourcemapped build>`; header comment has the rest).

## What the evidence says

1. **Read-mode page canvases are huge on desktop, and the main thread pays per pixel.** At
   1440×900 and DPR 2 a fit-width page is a 2688×3479 canvas (9.35 Mpx, 37 MB) under the
   whole-page cap `MAX_BITMAP_PIXELS = 4096²` (`engine/engine-service.ts:144`); the phone already
   caps at `COMPACT_BITMAP_PIXELS = 2048²` (`:154`) and covers the visible page with tiles. Six
   mounted canvases hold 56 Mpx, plus the same bitmaps again in the 150 MB cache
   (`bitmap-cache.ts:48`, one size for every device: PF-8's sizing is not built). The top
   main-thread JS function in both CPU profiles is `draw` → `context.drawImage(bitmap)`
   (`pages/PageCanvas.tsx:198-205`): 295 ms (desktop) and 681 ms (phone) of self time in one
   open + scroll. A trace of the scroll puts 10.7 s of main-thread self time in
   `CanvasResourceProviderSharedImage::ProduceCanvasResource` (1,405–5,486 calls in 300 frames)
   while a probe counted only 7 `drawImage` calls: the compositor re-snapshots the big canvases
   each frame. On SwiftShader that is a CPU copy; on a hardware GPU it is far cheaper, but the
   pixel count still sets PDFium's render time, upload size and memory everywhere.
2. **Closing documents does not give memory back.** After three open/close cycles the tab sits
   1.19 GB above Home while the JS heap grew 8 MB. A memory-infra dump after the closes still
   shows `GPU Process: gpu` 401 MB, shared memory ~400 MB on each side and `Renderer: canvas`
   107 MB; a heap snapshot finds **10 live `ImageBitmap`s and 16 canvases with no document open**
   (7 canvases, 10 bitmaps while one was open). Ending the two engine workers frees a further
   341–388 MB: PDFium's wasm heap grows for a 25 MB file and never shrinks while its worker
   lives. Phones cap a tab's canvas memory, so this is the path to a reload or a killed tab.
3. **The phone's open blocks for 0.8 s.** Long animation frames during open name: the Comlink
   reply handler (`comlink.mjs:169`, 256 ms/run: the open's continuation and first bitmaps'
   `drawImage`), `session-store` 135 ms (the snapshot), GPU glass `renderer.ts:754` 72 ms, the
   lazy `CompactApp` import 52 ms. The file is also copied on the main thread three times beyond
   the read: `new Blob([bytes])` to retain it (`engine/engine-service.ts:698`), then
   `sourceBytes` → `blob.arrayBuffer()` and `new Blob(...)` again for the snapshot
   (`session/session.ts:132-135`) before OPFS writes it; the OPFS callbacks show up in the first
   scroll after an open (210 ms of `getFileHandle` continuation in one desktop trace).
4. **GPU glass costs the phone's main thread while scrolling.** Same build, same document: TBT
   591 vs 81 ms, longest frame 217 vs 100 ms, 14 vs 8 long tasks. The per-frame callback
   (`glass-gpu/renderer.ts:754`, `frame` → `draw`) re-uploads each page canvas whose bitmap
   changed as a full-size mip-mapped texture (GLS-12), on the main thread, mid-scroll.
5. **First visit on a slow phone link takes a minute to be offline-ready** (52 s, 4.9 MB through
   the worker, 192 entries installed one at a time; R23 §1). Home itself is fine (3.0 s, 372 KB).
   Desktop Home loads 844 KB gzip of JS first (the full edition's `app` chunk, PF-11's target).
6. **One PDFium worker serialises everything.** Thumbnails (3.0 s for the mounted ones on 300
   pages), a zoom's sharp repaint (0.7–1.0 s) and the grid wait behind each other's renders;
   bigger page bitmaps (item 1) make each wait longer. PF-16 (a second worker on ≥ 8 GB) is the
   structural answer and is filed web-later.
7. **What is fine**: repeat visits (all from the worker, 4 KB), ink (8 ms event-to-draw, 21 ms
   commit), Save a copy and export (main thread mostly free: TBT ≤ 74 ms), typing in Find
   (worst key 88 ms), no blank pages seen while scrolling (PF-8's "never blank" holds).

## Ranked fixes (gain per effort)

Each has a done condition (before → target, from this baseline's measures) and the check. "S/M"
is the effort. Owners follow PRC-23: the lead settles technique and records the row; items that
amend a decision say so.

1. **Find and close the bitmaps that outlive their document** (S–M, engine/viewer lane).
   Heap-snapshot retainers of the 10 live `ImageBitmap`s after close (candidates: the
   `rendered`/clip tracking in `engine-service.ts:1145-1375`, paint-fade previews in
   `pages/paint-fade.ts`, the Home recents' first pages, glass textures), `close()` them on
   source close. Gain: ~400 MB back after closing documents. Done: `mem.after.ImageBitmap` = the
   Home count, `mem.leakPssMB` 1,193 → ≤ 800 (with fix 3: ≤ 300). Check:
   `baseline.ts --only memory --memory-dump --profiles desktop`; a unit test that a closed
   source leaves no open bitmap in the cache or tracker.
2. **A desktop whole-page budget like the phone's** (S, viewer lane; technique, lead). Cap Read
   mode's whole-page bitmap at ~4–6 MP on every edition and let `TiledPage` (already used above
   the budget) cover the visible page at exact scale, so the page in view stays as sharp as now.
   Gain: half the pixels per mounted page, faster first page and thumbnails (PDFium renders less),
   ~250 MB less while reading. Done: desktop `scroll.solid.canvasMpx` 56 → ≤ 28,
   `mem.openPssMB` 1,466 → ≤ 1,150, `large.thumbsMs` 3,008 → ≤ 2,300, `zoom.sharpMs` 702 →
   ≤ 600. Check: the baseline, plus a 1440×900 DPR 2 screenshot at fit width and 200 % (text
   edges unchanged: Q-bar), `canvas-zoom.spec.ts`, `viewer.spec.ts`.
3. **Let the engine workers go when no document is open** (S–M, engine lane). Terminate the
   PDFium and assembler workers after the last close (and on `pagehide` of an idle tab), start
   them again on the next open; PF-4's shared compiled module keeps the restart cheap. Gain: the
   ~370 MB wasm heaps. Done: `mem.workersHeldMB` 370 → ≤ 40 at Home after the closes, reopening
   the large PDF's first page within +150 ms of today's. Check: the baseline's memory section;
   `startup.spec.ts` (V1-P5/P6) for the reopen.
4. **Stop copying the file on the main thread, and write the snapshot after the first page**
   (S, engine + session lane). Retain the opened `File` (it is a Blob) instead of
   `new Blob([bytes])`; give the snapshot writer the retained Blob instead of
   `arrayBuffer()` + `new Blob` (`session/session.ts:132-135`), so OPFS streams it; queue the
   snapshot's first write for idle time after `first-page-bitmap`. Watch the File-changed-on-disk
   case (a `NotReadableError` on a later read): fall back to the copy only then. Gain: 75 MB less
   copying per 25 MB file, a shorter open on phones. Done (with 5): phone `large.openTbtMs`
   904 → ≤ 400. Check: baseline; `session.spec.ts`, `startup.spec.ts`, `save.spec.ts`.
5. **Keep the phone's open free of long tasks** (S–M, compact lane). After 4: start GPU glass
   texture work on the reader's first idle moment after the first page (GLS-12 already loads the
   renderer on idle; uploads should wait too), prefetch `CompactApp`/`overview` chunks during
   Library idle. Done: phone `large.openMaxTaskMs` 841 → ≤ 250, `large.openTbtMs` → ≤ 300.
   Check: baseline phone profile; `compact.spec.ts`, `compact-gpu-glass.spec.ts`.
6. **One fewer full-page pixel copy per render** (M, PF-7). Show page bitmaps through an
   `ImageBitmapRenderingContext` (`transferFromImageBitmap`) instead of a 2D `drawImage` copy;
   the canvas then owns the bitmap, so the cache keeps a reduced copy (PF-8's low-res
   placeholder) or re-requests on scroll-back; paint-fade cross-fades need a second element.
   Gain: the top JS hotspot (295/681 ms per open + scroll) and one 37 MB (desktop) copy per
   mounted page. Done: `drawImage` gone from the CPU profile's top 10, `canvasMpx` unchanged
   with memory −1 bitmap per mounted page. Check: PF-7's pixel-exact gate; `--cpu-profile`.
7. **Cheaper GPU-glass uploads** (M, glass lane; within GLS-12/14). The shader reads a blurred
   mip level, so upload a page reduced to the level it samples (a `createImageBitmap` resize,
   off the main thread) and only when the page under a piece changes. Done: phone
   `scroll.gpu.tbtMs` 591 → ≤ 1.5× `scroll.css.tbtMs`, `scroll.gpu.maxMs` 217 → ≤ 120.
   Check: `compact-gpu-glass.spec.ts`, `glass-pixels.spec.ts` (what the GPU sees, GLS-14).
8. **Phone first visit: precache by edition and register after the first page** (M; needs a
   PF-17 amendment, owner/lead). R23's P1 and P5. Done: phone `first.offlineReadyMs` 52 s →
   ≤ 35 s, `first.swKB` 4.9 → ≤ 3.8 MB, Home and sample times unchanged. Check: baseline phone
   `--only first`; `offline.spec.ts`.

Not ranked: a second read-only PDFium worker (PF-16) after 2 and 3 if thumbnails and zoom still
miss their targets; splitting the desktop `app` chunk (PF-11) for slow desktop links.

## Decisions that constrain the fixes

- **PF-7** (pixel-exact gate on one fewer copy), **PF-8** (cache sized to the device; trims to a
  low-res placeholder, never blank), **PF-16** (second worker, web-later), **PF-17** (every lazy
  chunk precached: fix 8 amends it), **PF-4** (shared compiled module: makes fix 3 cheap);
  PLAN.md §2.3 rows.
- **PRC-11** (bundle gates are not raised) and **PRC-20** (what the first paint loads): no fix
  here adds to the first paint.
- **GLS-5** (draw on change only), **GLS-10** (cost ladder, slow-frame rule), **GLS-12** (page
  raster as mip-mapped texture, renderer on idle), **GLS-13** (eligibility, fallback, test-only
  force), **GLS-14** (what the GPU sees, legibility floor): fix 7 must keep the glass looking the
  same and pass `glass-pixels`.
- **MOB-13** (all four samples precached) and R23's proposals, for fix 8. No MOB row limits the
  phone's bitmap budget beyond `COMPACT_BITMAP_PIXELS`, which fix 2 extends to desktop.

## Limits of this baseline

- No hardware GPU: scroll frame times are dominated by SwiftShader canvas snapshots; a real-GPU
  run (the owner's Mac or an Android phone with `chrome://inspect`) is needed for absolute
  frame numbers. The ratios (Clear vs Solid, GPU glass vs CSS+) and everything about pixels,
  bytes, memory and main-thread scripts carry over.
- Phone ink, zoom and thumbnails are not driven (the compact edition has its own pen spec and
  no sidebar); typing is measured in Find, not in a text box.
- The machine was shared; repeat the three runs on a quiet machine before comparing a fix.
