# Printing a PDF from the browser (spike, 2026-10-22)

Epic 5 lane 1 (`docs/company/epics-r25.md`): how Print… prints the exported PDF on each engine.
Decision PRD-25; code `export/print.ts`.

## Two methods

- **Frame.** The exported bytes as a blob URL in a hidden iframe, then
  `iframe.contentWindow.print()`. The browser's own PDF viewer prints: vector text, exact output,
  no rendering of ours. It needs a viewer and a same-origin frame.
- **Pages.** Each page rendered to a JPEG in a print-only sheet (`@media print` hides everything
  else), then `window.print()`. It works wherever printing works, and it costs memory and
  rasterises the text.

## Verdict per engine

| Engine | Method | Evidence |
| --- | --- | --- |
| Chromium desktop | Frame | Checked here (Chromium 1194, headless and headed): a blob PDF frame loads the viewer and `print` is reachable. Recto's CSP blocks it until it has `frame-src blob:`, because the frame falls back to `default-src 'self'`. `object-src 'none'` does not block the viewer. |
| Firefox desktop | Frame, falling back to Pages | pdf.js runs in the frame and takes over `print()`. Not checked here (only Chromium is installed). If the frame's window refuses access, the code catches it and prints Pages. |
| Safari macOS | Pages | WebKit's PDF view in a frame prints blank or prints the parent page. |
| iPadOS / iOS | Pages | The frame does not print at all. `window.print()` returns at once, so the sheet is removed on `afterprint`. |
| Android Chrome | Pages | It has no PDF viewer (`pdfViewerEnabled` is false). |

**Choice by feature, not by user agent.** Frame is used when `navigator.pdfViewerEnabled === true`
and the browser is not WebKit. WebKit is told by `GestureEvent` or `navigator.standalone`, which
only WebKit ships. Anything else prints Pages, and so does a frame that fails.

## Memory at 400 pages

Lazy images do not help: the print snapshot needs every image decoded before `window.print()`,
and browsers treat `loading="lazy"` differently when printing. So the pages render one after
another, and only one bitmap is alive at a time; each page is kept as a JPEG blob (q 0.92).
They render at 150 dpi while all the pages together stay under a budget of 240 MP of decoded
pixels (about 1 GB as RGBA). Longer documents get a lower dpi, never below 72. Letter at 150 dpi
is 2.1 MP a page, so 400 pages would need 3.4 GB. Under the budget, 400 pages print at about 80
dpi, and 100 pages still print at 150. The job capsule shows the progress, and Cancel stops at
the next page.

**Not tested:** Firefox, Safari and the iPad on real devices. Check them before shipping.
